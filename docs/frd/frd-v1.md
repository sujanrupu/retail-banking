# BankSphere Functional Requirement Document

## 1. System Overview
This document specifies the functional and non-functional requirements for BankSphere — Retail Banking Platform.

## 2. Functional Requirements
1. FR-1: Customer Registration – The system shall accept a POST /api/v1/customers with unique email, username, and hashed password; it shall return 201 with customerId and activationToken, enforce email uniqueness, password complexity (≥12 chars, 1 upper, 1 lower, 1 digit, 1 special), and optional MFA setup flag. 2. FR-2: Authentication – The system shall issue JWT access tokens via POST /api/v1/auth/login with email/username and password; tokens expire 30 min, refresh tokens 7 days; MFA challenge required for admin logins. 3. FR-3: RBAC Enforcement – All endpoints shall validate JWT scopes; customers may access /accounts, /transfers; admins may access /admin/* and /accounts/* with write privileges. 4. FR-4: Account Creation – Admins may POST /api/v1/admin/accounts with customerId, accountType, initialBalance; system creates account with status ACTIVE, audit log entry, returns 201 with accountId. 5. FR-5: Account State Transitions – Admins may PATCH /api/v1/admin/accounts/{id} with status {DEACTIVATE, FREEZE, UNFREEZE}; system validates current status, updates, logs immutable event, returns 200. 6. FR-6: Funds Transfer – Customers may POST /api/v1/transfers with sourceAccountId, destinationAccountId, amountCents; system validates balance ≥ amount, status ACTIVE, single‑day limit < $10,000, single‑transaction limit < $5,000, performs AML check, creates pending transaction, returns 202. 7. FR-7: Transaction Settlement – Background worker processes pending transfers within 5 s, updates balances atomically, emits audit log, returns 200. 8. FR-8: Audit Trail – Every critical action writes an immutable record to audit_log with eventId (UUID), eventType, timestamp, userId, payload JSON; records are WORM stored, hashed, and retained 7 years. 9. FR-9: Admin Dashboard Data – GET /api/v1/admin/metrics returns JSON with activeAccounts, pendingFreezes, dailyTransferVolume, auditLogCount; supports pagination and filtering by date. 10. FR-10: WCAG 2.1 AA UI – All UI routes must expose semantic ARIA labels, color contrast ≥4.5:1, and keyboard navigation; automated Lighthouse score ≥90.

## 3. API Requirements
- POST /api/v1/customers – Create customer; Auth: none; Body: email, username, password, mfaEnabled (bool); Response: 201 {customerId, activationToken}; Errors: 400 (validation), 409 (duplicate). - POST /api/v1/auth/login – Authenticate; Auth: none; Body: emailOrUsername, password; Response: 200 {accessToken, refreshToken}; Errors: 400, 401. - POST /api/v1/auth/mfa – Verify MFA; Auth: JWT (admin only); Body: token; Response: 200 {accessToken}; Errors: 400, 401. - GET /api/v1/accounts – List customer accounts; Auth: JWT (customer); Response: 200 [{accountId, balanceCents, status}]; Errors: 401. - GET /api/v1/accounts/{id} – Get account details; Auth: JWT (customer/admin); Response: 200 {accountId, balanceCents, status, history[]}; Errors: 401, 404. - POST /api/v1/admin/accounts – Create account; Auth: JWT (admin); Body: customerId, accountType, initialBalanceCents; Response: 201 {accountId}; Errors: 400, 401, 403. - PATCH /api/v1/admin/accounts/{id} – Update status; Auth: JWT (admin); Body: status; Response: 200; Errors: 400, 401, 403, 404. - POST /api/v1/transfers – Initiate transfer; Auth: JWT (customer); Body: sourceAccountId, destinationAccountId, amountCents; Response: 202 {transferId, status: PENDING}; Errors: 400, 401, 403, 429, 500. - GET /api/v1/admin/metrics – Dashboard metrics; Auth: JWT (admin); Response: 200 {activeAccounts, pendingFreezes, dailyTransferVolume, auditLogCount}; Errors: 401, 403.

## 4. Data Model
- customers: id(UUID PK), email(VARCHAR(255) UNIQUE NOT NULL), username(VARCHAR(50) UNIQUE NOT NULL), passwordHash(VARCHAR(255) NOT NULL), mfaEnabled(BOOLEAN NOT NULL), createdAt(TIMESTAMP NOT NULL), updatedAt(TIMESTAMP NOT NULL). - accounts: id(UUID PK), customerId(UUID FK NOT NULL REFERENCES customers(id)), accountType(VARCHAR(20) NOT NULL), balanceCents(BIGINT NOT NULL DEFAULT 0), status(VARCHAR(20) NOT NULL), createdAt, updatedAt. - transfers: id(UUID PK), sourceAccountId(UUID FK NOT NULL REFERENCES accounts(id)), destinationAccountId(UUID FK NOT NULL REFERENCES accounts(id)), amountCents(BIGINT NOT NULL), status(VARCHAR(20) NOT NULL), createdAt, processedAt. - audit_log: eventId(UUID PK), eventType(VARCHAR(50) NOT NULL), userId(UUID FK REFERENCES customers(id)), payload(JSONB NOT NULL), createdAt(TIMESTAMP NOT NULL), hash(VARCHAR(64) NOT NULL). Relationships: customers 1‑many accounts; accounts 1‑many transfers (as source or destination).

## 5. Non-Functional Requirements
- Performance: Average end‑to‑end latency ≤200 ms for all public APIs, 95th percentile ≤350 ms. - Scalability: Handle ≥5,000 concurrent authenticated users; horizontal scaling via stateless services; autoscale target 10% buffer. - Availability: 99.99 % uptime SLA, 4‑hour RTO for critical services, 24‑hour MTTR. - Reliability: 99.9 % data consistency, idempotent POST/PUT operations, retry‑safe transfer processing. - Maintainability: Code coverage ≥80 %, automated unit/integration tests, CI pipeline with static analysis, versioned API (v1). - Usability: WCAG 2.1 AA compliance, responsive design, API documentation via OpenAPI 3.0. - Compliance: PCI‑DSS Level 1 for card data (if applicable), SOC 2 Type II, GDPR data subject rights, US‑FSR for AML checks.

## 6. Security Requirements
- AuthN: JWT bearer tokens signed with RS256, key rotation every 90 days. - AuthZ: RBAC scopes encoded in JWT; admin scopes: admin:read, admin:write; customer scopes: account:read, transfer:write. - Encryption: TLS 1.3 for all transport; AES‑256 GCM for database encryption at rest; KMS key management. - Input validation: JSON schema validation, OWASP Top‑10 mitigations, rate limit 100 requests/min per IP, 10 per second per user. - Secrets: Stored in cloud secrets manager, rotated quarterly. - Audit: Immutable WORM storage, SHA‑256 hash chain, 7‑year retention, tamper‑evidence logs. - MFA: TOTP via RFC 6238, email OTP with 6‑digit code, 5‑minute expiry.
